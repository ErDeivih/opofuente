## Qué he construido

Un monorepo local con backend FastAPI por capas y frontend React/TypeScript/Vite, capaz de
arrancar, migrar su base de datos desde cero y **declarar honestamente su propio estado** mediante
`/health/ready`, `/capabilities` y `/settings`. La interfaz muestra ese estado real y, para cada una
de las ocho secciones que aún no existen, dice a qué slice pertenecen en lugar de aparentar
funcionalidad. Las quince puertas de calidad se ejecutan con un solo comando (`scripts/gates.ps1`) y
están también definidas para CI, con el contrato OpenAPI generado y los tipos TypeScript derivados
comprobados en ambos lados.

## Cómo fluye la información

### Petición HTTP

1. `uvicorn` sirve `opofuente.main:app`. El `lifespan` crea el árbol de `data/`, configura los logs
   JSON y, al terminar, libera el motor de SQLite.
2. Cadena de middlewares ASGI, de dentro hacia fuera: **CORS** → **cabeceras de seguridad** →
   **comprobación de Origin** → **identificador de correlación**. El último en añadirse es el más
   externo, así que un rechazo por Origin también devuelve `X-Correlation-ID`.
3. `api_router` monta `routes/system.py` bajo `/api/v1`. Las rutas obtienen `Settings` y
   `SystemService` de `request.app.state` mediante dependencias anotadas (`api/deps.py`), no de
   singletons: eso es lo que permite levantar una aplicación completa contra un directorio temporal.
4. `SystemService.readiness()` ejecuta las sondas (`DatabaseProbe`, `DataDirectoryProbe`) y
   `SystemService.capabilities()` agrega los proveedores (`ConfigurationCapabilityProvider`,
   `SqliteCapabilityProvider`, `PlannedCapabilityProvider`).
5. Las sondas hablan con la infraestructura: `DatabaseProbe` abre una sesión SQLAlchemy y comprueba
   conexión, revisión de Alembic, `PRAGMA foreign_keys`, `journal_mode` y que `app_metadata` tenga
   filas. `SqliteCapabilityProvider` crea y destruye una tabla virtual FTS5 en `temp` para verificar
   de verdad el soporte de este SQLite.
6. La capa API traduce los objetos de dominio a DTO (`api/schemas.py`) y devuelve JSON; los errores
   salen como `application/problem+json` (RFC 9457) desde `api/errors.py`.

### Frontend

`main.tsx` → `App` (QueryClientProvider + BrowserRouter) → `AppShell` → `AppRoutes`. Las páginas no
llaman a `fetch`: usan hooks de `src/api/queries.ts`, que llaman a `src/api/system.ts`, que usan
`src/api/client.ts`. Ese cliente tipa sus respuestas con los tipos **generados** desde OpenAPI
(`@opofuente/contracts`), de modo que un cambio de contrato rompe el typecheck.

### Contrato

`FastAPI.openapi()` → `uv run python -m opofuente.tools.export_openapi` →
`packages/contracts/openapi.json` → `npm run contracts:generate` →
`packages/contracts/src/openapi.d.ts` → typecheck del frontend. Dos puertas impiden la deriva: una
prueba de contrato en pytest y `npm run contracts:check` (ADR-002).

## Patrones y decisiones aplicadas

- **Composición explícita en `create_app(settings)`**: todo el estado va a `app.state`. Es lo que
  permite que las pruebas y el E2E usen directorios temporales sin variables globales.
- **Hexagonal / puertos y adaptadores**: el dominio no conoce FastAPI ni SQLAlchemy; las sondas y
  proveedores de capacidades implementan `Protocol`s de la capa de aplicación.
- **Estado de capacidad explícito** (`enabled`, `disabled`, `unavailable`,
  `configured_unverified`, `planned`): impide presentar como operativo lo que no existe, que es la
  trampa que el plan de pruebas prohíbe.
- **Middleware ASGI puro** en lugar de `BaseHTTPMiddleware`, para no romper SSE cuando llegue S09.
- **Logs con lista blanca de campos** (`SAFE_EXTRA_KEYS`) y solo el tipo de excepción: un `extra`
  inesperado se descarta en lugar de filtrarse; de una traza se pierde el detalle, y se acepta a
  cambio de no registrar contenido privado.
- **Dependencias inyectadas anotadas** (`Annotated[T, Depends(...)]`), no llamadas en valores por
  defecto (lo exige `ruff B008`).
- **ADR-001** (uv y npm workspaces), **ADR-002** (OpenAPI como fuente de verdad), **ADR-003**
  (endurecimiento HTTP local, pendiente de revisión del propietario), **ADR-004** (TypeScript
  fijado a 5.9.x).

## Seguridad y privacidad

| Regla | Cómo se cumple | Evidencia |
|---|---|---|
| Solo loopback | `Settings` rechaza cualquier host que no sea `127.0.0.1`, `::1` o `localhost` | prueba unitaria + mensaje de error |

| Logs sin contenido | lista blanca de campos; solo el tipo de excepción | pruebas unitarias del formateador |
| Datos fuera de git | `.env`, `data/`, `.e2e-data/`, `.gates-data/`, modelos y `*.sqlite3` ignorados | comprobado con `git check-ignore` |

## Limitaciones conocidas

1. **No hay entidades de negocio, ingestión, OCR, IA ni pantallas de producto.** S00 no las incluye;
   la interfaz lo dice en lugar de simularlas.
2. **`PATCH /settings` no existe.** `/settings` responde con `editable: false`; el almacén de ajustes
   persistido corresponde a un slice posterior. Implementar un `PATCH` que solo cambie estado en
   memoria sería un botón falso.
3. **La CSP no protege el HTML del SPA.** En desarrollo y preview lo sirve Vite. La CSP del
   documento llega cuando el backend sirva el frontend construido (S12).
4. **No hay autenticación.** Es una decisión aceptada solo para loopback y un usuario; ADR-003 está
   *pendiente de revisión del propietario*, y cualquier uso en LAN o nube exige un proyecto aparte.
5. **El flujo de CI está escrito pero nunca se ha ejecutado**: no hay remoto de GitHub. Se validó el
   YAML con un analizador y se ejecutaron localmente los mismos pasos en Windows.
6. **Aviso de obsolescencia de Starlette**: `fastapi.testclient` usa `httpx` y Starlette 1.6 avisa de
   que prefiere `httpx2`. No afecta a las pruebas, pero conviene revisarlo cuando el ecosistema lo
   estabilice; no se ha añadido una dependencia nueva por un aviso.
7. **`pytest` usa `--basetemp=.pytest-tmp`.** La raíz de temporales de este equipo
   (`…\Temp\pytest-of-David`) es propiedad de `SYSTEM` por un proceso elevado anterior y no se puede
   limpiar sin ser administrador. La suite es hermética, pero **no se pueden ejecutar dos sesiones de
   pytest en paralelo** en el mismo repositorio.
8. **`apps/api/opofuente/workers/` está vacío a propósito** (S02). Igual que `fixtures/synthetic/`,
   que solo contiene su README.
9. **`docs/product-spec/` es una copia.** Si el paquete original cambia, hay que volver a copiarlo;
   no hay sincronización automática ni comprobación de que coincidan.
10. **TypeScript queda en 5.9.x** por incompatibilidad real de `openapi-typescript` y
    `typescript-eslint` con el compilador nativo 7 (ADR-004).

## Qué se rompe si cambias X

| Cambio | Qué falla y por qué |
|---|---|
| Añadir o renombrar una ruta de la API sin regenerar | puerta 8 (contrato commiteado) y puerta 10 (`contracts:check`), y el typecheck si el frontend la usa |
| Regenerar solo `openapi.json` y no los tipos | puerta 10 (`contracts:check`) |
| Cambiar `CapabilityStatus` | prueba de contrato que fija el enum exacto y `statusBadges.ts` del frontend |
| Cambiar el orden de `add_middleware` | pruebas de Origin y de correlación; los rechazos dejarían de devolver `X-Correlation-ID` |
| Permitir hosts no loopback en `Settings` | prueba unitaria de configuración; rompe la frontera de seguridad de ADR-003 |
| Quitar `app_metadata` o su migración | `/health/ready` devuelve 503 y la prueba de integración falla |
| Registrar un `extra` nuevo en un log con contenido | el formateador lo descarta; el campo no aparecerá (comportamiento buscado) |
| Usar `BaseHTTPMiddleware` en lugar de los middlewares ASGI | el SSE de S09 podría bloquearse; hoy no hay pruebas que lo detecten |
| Mover la lógica de sondas a la capa API | se pierde la posibilidad de probar el informe sin HTTP y el diseño hexagonal |

## Qué criticaría un revisor senior

1. **El 503 de `/health/ready` no está tipado de verdad.** El cuerpo añade `checks` como miembro de
   extensión de RFC 9457 y el frontend lo lee con un `as { checks?: CheckResult[] }` escrito a mano
   (`src/api/system.ts`). El contrato declara `ProblemDetail` y `ReadinessSchema`, pero no el caso
   degradado. La solución correcta es un esquema `ReadinessProblem` en el contrato, y no hacerlo en
   S00 deja la única conversión sin verificar por el compilador en todo el camino API→UI.
2. **La lista de puertas está duplicada.** `scripts/gates.ps1` y `.github/workflows/ci.yml`
   describen los mismos pasos por separado y pueden divergir en silencio; además el flujo de CI no se
   ha ejecutado nunca, así que su valor hoy es documental. Un único origen (por ejemplo, generar los
   pasos de CI desde el script, o usar el script en CI con PowerShell) sería más honesto.
3. **La sonda de base de datos comprueba detalles de implementación** (`journal_mode=wal`,
   `foreign_keys=ON`) y afirma el resultado como readiness del producto. Es correcto hoy, pero mezcla
   "la configuración está aplicada" con "la aplicación puede trabajar"; si algún día se cambia de
   motor, hay que rehacer la sonda entera.
